# The Final Mental Model

*Framework questions: {doc}`../../framework/12-mental-model`*

## Answer

- **Why does it exist?** To get memory safety and thread safety without a garbage collector and without a run time, so large systems code stops dying of bugs that C leaves to vigilance and GC languages defer to pauses.
- **What can programs represent?** Statically typed values of every shape - primitives, structs, tuples, arrays, data-carrying enums, references, closures, trait objects - combined as products and alternatives, with absence modeled as `Option` rather than null and value parameters limited to const generics.
- **What does source code mean?** Eager call-by-value evaluation of typed expressions under a specified evaluation order, after macros are expanded, code is desugared, and the ownership/borrow discipline is proved; blocks are expressions, items are order-independent, and the meaning of a crate is the behavior of `main` plus its spawned threads and tasks.
- **What does a name refer to?** A place - a typed location in memory - bound lexically with shadowing, resolved through separate type/value/macro/lifetime namespaces, and aliased only as the borrow checker permits: many shared borrows or one exclusive borrow, never both.
- **How does computation proceed?** By control flow over eager evaluation, with laziness available on demand (iterators, closures, `LazyLock`) and suspension available through `async` state machines polled by an external executor; backtracking must be hand-written, and recursion is unbounded only until the stack overflows.
- **How is behavior defined and composed?** As functions, methods, trait methods, and closures - all first-class values - combined by chaining combinators and stacking trait bounds rather than by nesting callbacks or composing operators.
- **How are abstractions formed?** Generic parameters and trait bounds generalize types, const generics generalize values, modules and `pub` variants control what is visible, macros abstract over syntax, and monomorphization erases the cost of all of it at compile time.
- **What can change?** Only what ownership or an exclusive borrow allows: `mut` is opt-in, sharing means immutability unless `Cell`/`RefCell`/atomics/locks declare otherwise, and the compiler proves that readers and writers never overlap unsynchronized.
- **What is the lifetime of a thing?** Exactly as long as its single owner keeps it: values are created with their owner, moved on transfer, and dropped by compiler-inserted RAII glue when the owner dies - no collector, no refcount unless you ask for one, with `Rc`/`Arc`/`Weak` for shared and cyclic shapes.
- **How does failure work?** Failure is data: `Option` for absence, `Result` for errors, `?` to propagate, exhaustive `match` to recover; panics are for broken invariants and unwind or abort, and only `unsafe` code can produce undefined behavior.
- **How does the program interact with the world?** Through ordinary libraries over `std` traits - `Read`/`Write`, `fs`, `net`, `process`, time - with `unsafe` `extern "C"` as the FFI boundary and RAII handles tying every external resource to a scope; randomness and async I/O come from crates, not the language.
- **How do multiple computations coexist?** OS threads run in real parallelism and communicate by channels or locked shared state, while async tasks interleave under an executor's schedule; `Send`/`Sync` plus ownership make data races a compile error, leaving only logical races to test for.
- **What does the language know before execution?** Types, trait resolution, lifetimes and borrow regions, exhaustiveness, mutability, `Send`/`Sync`, and const-evaluated values; run time is reserved for data, dispatch targets, lock and `RefCell` outcomes, panics, I/O, and scheduling.
- **What does it guarantee?** For safe code: no use-after-free, no double free, no dangling or null references, no data races, and exactly-once destruction; those guarantees are bypassable only inside `unsafe`, where the programmer owes the documented contract, and functional correctness remains yours to test.
- **What can programs do about programs?** Inspect and generate syntax at compile time - token-pattern macros, procedural macros over parsed ASTs, build scripts, const evaluation - but never reflect over code at run time; metadata lives in attributes, doc tests, and lints rather than in proof terms.
- **How do programs scale?** Modules and crates with default-private visibility form the unit of both compilation and architecture, Cargo and crates.io handle dependency versions and features, and workspaces enforce layering that the compiler itself will not let you violate.
- **How does source become execution?** rustc parses and expands, checks names/types/borrows, lowers to MIR, monomorphizes, hands control to LLVM, and links native object files - ahead of time, with lifetimes and generics erased and no bytecode or virtual machine anywhere in the path.
- **What style does it make natural?** Types-first, data-modeling style: small enums plus exhaustive matching, newtypes, RAII, iterator pipelines, errors as values, and the habit of asking "who owns this?" before "who can touch this?" - while inheritance, reflection, and pervasive shared mutation feel foreign.
- **What makes it unusual?** It moved the memory-safety argument out of the run time and into the type system: an affine ownership-and-borrows discipline, checked before execution and quarantining every unsafe operation behind an explicit door, buys the guarantees of a garbage-collected language with the footprint of C.

## Rust Without Feature Lists

A Rust program is a claim about ownership. Someone is responsible for every byte, that responsibility moves exactly once when a value moves, and everyone else is merely visiting under terms the compiler has already verified. What feels like the language's subject is therefore not data or objects but authority: who may read, who may write, who must clean up, and for how long each of those permissions lasts. Exceptions are ordinary values rather than stack-unwinding magic, and anything the checker cannot verify - foreign calls, raw pointers, hardware registers - is pushed behind a door the programmer must open visibly and defend personally.

Because authority is checked before anything runs, the style that emerges is design-by-representation: you make illegal states unconstructible, make resources owned so that scope exit is cleanup, and make sharing explicit so that threads are an ordinary consumer of types rather than a hazard zone. Abstraction is safe to use freely because it is compiled away - the description and the machine code cost the same - so the programmer composes traits and iterators the way other languages compose machine instructions, with the compiler re-verifying every use site as the codebase grows.

The resulting language is conservative in what it demands of the machine and radical in what it demands of the programmer: no collector, no mandatory run time, native ahead-of-time code, in exchange for accepting that some designs must be rewritten until ownership lines up. That trade - safety as a static, checkable property rather than a run-time service - is the single idea everything else in the language orbits.

## What the Map Missed

- "What is the lifetime of a thing?" treats lifetime as duration, but Rust's real axis is *authority over a place*: a value can outlive every borrow of it, a borrow can outlive nothing it points at, and the interesting failures are about permissions (aliasing versus mutation, use-after-move) rather than about time alone. The map has no question that asks "who is allowed to touch this, and at the same time as whom?"
- The map underweights ecosystems and tooling as first-class answers. For Rust, cargo, crates.io, rustdoc with doctests, clippy, rustfmt, and Miri are not accessories - they are how the language's guarantees are actually delivered and enforced in practice, yet no universal question asks "what machinery surrounds the compiler?"
- Send/Sync do not fit any single category: they are compile-time knowledge (VI), concurrency mechanism (V), and uniqueness mechanism (XI) at once, auto-derived from type structure rather than written by programmers. The map's one-question-one-section shape struggles with guarantees that emerge from the interaction of sections instead of living inside one.
